# Auditoría continua — integraciones de conversaciones (2026-10-14)

**Fuente:** rama `main` de GitHub posterior a PR #145. **Alcance:** inspección estática del flujo WhatsApp/Messenger/Instagram y workflow n8n. **Estado:** revisión parcial; sin pruebas de integración ejecutadas ni validación de credenciales de Meta. Este documento registra evidencia, no declara producción lista.

## Hallazgos priorizados

### CH-001 — Alto: mensajes fallidos pueden quedar marcados como duplicados
- `backend/app/routers/channel_integrations.py`, `_handle_channel_webhook` llama `_is_duplicate_message_db` **antes** de `_process_incoming_event`.
- `_is_duplicate_message_db` inserta y confirma `ProcessedMessage` antes de generar y enviar la respuesta. Si el envío o generación falla, el `except` del webhook solo agrega el error a `failed` y no libera el registro.
- Un reintento del mismo evento encuentra `message_id` y se omite. Riesgo: conversación sin respuesta aun con reentrega de Meta.
- El modelo `ProcessedMessage` ya dispone de `delivery_status` y `reply_text`, pero el camino anterior no los utiliza para recuperación.
- **Acción:** implementar reclamo transaccional y estados `processing/pending_delivery/delivered` con recuperación e idempotencia; agregar pruebas de fallo y reentrega concurrente.

### CH-002 — Alto: prueba de WhatsApp usa dominio equivocado
- `backend/app/routers/channel_integrations.py`, `test_channel_connection`, rama `whatsapp`: consulta `https://graph.instagram.com/v18.0/{phone_id}` con `phone_number_id` de WhatsApp.
- La entrega real usa `https://graph.facebook.com/v23.0/{phone_number_id}/messages`. La prueba no comprueba el servicio correcto y puede reportar fallos falsos.
- **Acción:** verificar contra endpoint oficial de WhatsApp Graph con versión y credenciales coherentes; prueba simulada del URL.

### CH-003 — Medio: campos de token de Instagram no son consistentes
- `_channel_health_snapshot_with_profiles` exige `instagram_account_id` y `page_access_token`.
- `test_channel_connection` exige `instagram_account_id` y `access_token`.
- `_send_meta_page_reply` utiliza `page_access_token` para Instagram y Messenger.
- **Acción:** definir esquema canónico por canal, compatibilidad y tests de configuración/entrega.

### CH-004 — Alto: la verificación de firma de webhooks puede quedar deshabilitada
- `_verify_meta_signature` devuelve sin validar cuando `META_APP_SECRET` no está configurado.
- El diagnóstico informa `signature_validation_enabled`, pero no exige el secreto en este camino.
- **Acción:** establecer fallo seguro para entornos de producción y pruebas de rechazo de peticiones no firmadas; verificar configuración real sin exponer secretos.

### CH-005 — Medio: workflow n8n no demuestra respuesta saliente a WhatsApp
- `docs/n8n/whatsapp_ai_flow.json` conecta un nodo `respondToWebhook`, pero no contiene nodo de envío a Meta Graph API.
- `POST /api/ai/training-queue` en n8n debe cotejarse con rutas reales y esquemas del backend antes de utilizar el flujo.
- El webhook nativo de `channel_integrations.py` sí implementa envío a Meta, por lo que hay dos arquitecturas potenciales: decidir cuál es la ruta oficial antes de activar n8n.
- **Acción:** inventariar contratos, elegir arquitectura, probar entrada→IA→respuesta→reintento en staging.

### CH-006 — Medio: deduplicación no separa canales/cuentas
- `ProcessedMessage.message_id` tiene unicidad global y `_is_duplicate_message_db` consulta solo `message_id`.
- Si identificadores coinciden entre proveedores/cuentas, un mensaje distinto puede omitirse.
- **Acción:** usar clave compuesta `channel/account/message_id` con migración compatible y pruebas; verificar formato real de IDs antes de cambiar esquema.
